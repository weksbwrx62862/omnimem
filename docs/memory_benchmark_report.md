## 三、根因分析：为什么向量检索反而降低了分数

### 3.1 核心矛盾：向量语义相似 ≠ 答案相关

向量检索返回"语义相似"的结果，但 LongMemEval 的 QA 评估需要"精确包含答案"的结果。当向量返回语义相关但不含精确答案的结果时，会挤掉 BM25 的精确匹配结果。

**具体表现**：
- multi-session：v3 BM25 精确匹配 → Session Hit 70%，v4 向量噪声覆盖 → Session Hit 10%
- preference：v3 BM25 精确匹配 → Session Hit 80%，v4 向量噪声覆盖 → Session Hit 60%

### 3.2 RRF 融合问题

当向量通道返回大量"低分但语义相关"的结果时，RRF 融合会给予这些结果不适当的高权重，将 BM25 的精确匹配挤出 top-k。

### 3.3 Ingest 时间暴增

向量 embedding 计算每条记忆需要 ~0.3s（GPU 不可用），每题平均 90+ 条记忆 → 27s 仅用于 embedding。这是向量检索的固有开销。

## 四、改进方向

### 4.1 短期：RRF 通道权重调优

| 方案 | 描述 | 预期效果 |
|:---|:---|:---|
| **降低向量通道权重** | 在 RRF 融合中给 BM25 更高权重（如 BM25: 0.7, Vector: 0.3） | multi-session Session Hit 回升 |
| **向量 min_score 阈值** | 提高向量检索的最低相似度阈值（如 0.5→0.6） | 减少低质量向量结果干扰 |

### 4.2 中期：检索策略改进

| 方案 | 描述 | 预期效果 |
|:---|:---|:---|
| **分阶段检索** | 先用 BM25 检索精确匹配，再用向量补充语义匹配 | 兼顾精确和语义 |
| **per-query 通道选择** | 对事实型查询偏 BM25，对语义型查询偏向量 | 各维度优化 |
| **答案验证** | 在 LLM generation 前用检索结果验证相关性 | 提升 QA 正确率 |

### 4.3 长期：架构改进

| 方案 | 描述 | 预期效果 |
|:---|:---|:---|
| **分层记忆提取** | 类似 Mem0，先提取高质量记忆再检索 | 整体 QA 40%+ |
| **KG 图谱检索** | 实现 _GraphRetriever，利用时序图谱回答时序问题 | temporal-reasoning 突破 |
| **LLM 查询改写** | 对查询进行分解和改写，提升多跳推理 | multi-session 突破 |

## 七、关键洞察

1. **BM25-only 反而优于混合检索**：v3 (15%) > v4 (11.67%)，说明当前 RRF 融合策略未能有效利用向量检索的优势。

2. **向量检索的价值在 assistant 维度**：v4 的 assistant QA (30%) > v3 (10%)，因为 assistant turn 的信息需要语义匹配才能有效检索。

3. **当前最大瓶颈是 RRF 融合策略**：需要给 BM25 精确匹配更高的权重，避免向量噪声覆盖。

4. **长期方向是分层记忆提取**：Mem0 的核心优势不在检索算法，而在记忆质量——先从对话中提取高质量记忆，再检索。这是 OmniMem 需要学习的。
